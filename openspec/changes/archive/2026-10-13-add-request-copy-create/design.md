## Context

参见 `proposal.md` 的动机说明。当前 Request List 已在每行 Actions 中提供 View 和按权限启用的 Edit；Configuration 页面通过 `edit` 查询参数加载 Request 详情，并在同一页面内完成详情到表单的字段映射。提交逻辑已经明确分为更新现有 Request 和创建新 Request 两个分支。

源 Request 详情包含请求级元数据和嵌套的 `configData`。复制功能必须复用配置回填，但不能把源 Request 对象作为新建参数基础，否则当前或未来新增的请求级字段可能被意外提交。

## Goals / Non-Goals

**Goals:**

- 在不新增后端接口的前提下支持从列表进入复制新建模式。
- 复用现有 Request 详情查询和编辑表单回填行为，避免维护两套字段映射。
- 让复制模式与普通新建共用相同的新建参数构造和提交路径。
- 通过白名单构造阻断源 Request 的请求级身份、流程和审计字段进入新建接口。

**Non-Goals:**

- 本次不定义或实现 PID、Barcode、Order ID 等业务字段的自动清空规则。
- 本次不定义证书、上传文件及其他嵌套资源 ID 是否复用的业务策略。
- 不新增复制专用后端接口，不记录 `copiedFromRequestId`，不改变后端数据模型。
- 不调整模板的保存、应用、变量或使用次数逻辑。

## Decisions

### 1. 使用独立的复制模式路由参数

Request List 的按钮导航到 `/configuration?copy=<request-id>`。Configuration 页面分别识别普通新建、编辑、模板和复制模式；复制参数只表示数据来源，不赋予更新源 Request 的语义。

选择该方案是因为现有页面已经以查询参数管理编辑和模板模式，新增 `copy` 与当前路由约定一致。替代方案是在浏览器状态或全局 Store 中传递源数据，但刷新页面会丢失状态，也无法直接分享或恢复复制页面。

若 URL 被手工构造成同时包含 `copy` 和 `edit`，复制模式优先，确保页面不会因歧义误更新源 Request。正常 UI 只生成单一模式参数。

### 2. 共享详情加载与表单回填，不共享保存语义

页面以复制 ID 或编辑 ID 作为详情查询来源，并让两种模式进入同一套 Request-to-form 映射逻辑。编辑模式保存走更新分支；复制模式与普通新建走创建分支。

选择共享回填逻辑是为了避免字段增加后编辑与复制出现映射差异。替代方案是为复制单独实现回填函数，但会形成重复代码和长期漂移风险。

### 3. 从表单状态白名单构造新建参数

新建提交参数由当前 `formData`、重新构造的 `configData` 和当前标签显式组成，并满足 `CreateRequestRequest` 类型。复制模式不得展开 `existingRequest`，不得复制后再删除字段，也不得把详情响应直接传给 `createRequest`。

普通新建和复制新建共用同一个 create payload 构造路径。这样 Request ID、Config ID、状态、负责人、时间戳、创建人、评论、历史和同步状态不会因为详情模型扩展而自动进入创建请求。

选择白名单构造是因为它对未来字段扩展默认安全；黑名单删除需要持续追踪详情模型中新加入的字段，漏删风险更高。

### 4. 复用现有后端接口和权限检查

复制模式通过现有详情接口加载源 Request，并通过现有创建接口保存。详情读取权限继续由后端控制；前端在加载失败时阻止提交未完整加载的副本。复制按钮与 View 同处 Actions 区域，是否可读取源详情仍以服务端响应为准。

不新增复制接口可以保持基础版本范围最小。未来如果需要服务端统一清洗字段、记录复制来源或实施嵌套资源复制策略，再单独引入复制草稿或复制创建接口。

### 5. 明确加载失败状态

复制模式只有在源 Request 成功加载并完成表单回填后才允许提交。加载期间禁用保存；404、403 或网络错误显示明确反馈，避免用户误以为空白表单代表源 Request 内容。

## Risks / Trade-offs

- [现有编辑回填逻辑体积较大，复制模式直接复用会继承其字段映射缺陷] -> 实现时只抽取或共享已有映射，不另写第二份映射，并以代表性配置字段验证回填结果。
- [白名单仅能阻断 Request 顶层元数据，`configData` 内仍可能包含文件或证书资源 ID] -> 本次按已确认范围保留现有表单行为，并在后续业务规则明确后单独制定嵌套字段清理策略。
- [列表 Actions 新增按钮可能压缩现有表格空间] -> 沿用紧凑按钮样式并验证常用视口下无重叠或不可操作情况。
- [手工构造冲突查询参数可能触发错误模式] -> 明确复制优先，并让所有更新判断只依赖有效的编辑模式状态。
- [复制按钮允许读取不属于当前用户的 Request] -> 不绕过现有详情接口权限；若后续需要更严格的复制权限，应由独立需求定义并由服务端强制执行。

## Migration Plan

1. 部署前端改动，不迁移现有数据，也不修改后端接口。
2. 验证普通新建、编辑、模板新建和复制新建四种入口。
3. 若需回滚，仅回退前端复制入口和复制模式处理；现有 Request 数据不受影响。

## Open Questions

- PID、Barcode、Order ID 等字段未来是否在进入复制模式时自动清空。
- 证书、批量文件、扩展文件等嵌套资源 ID 是否允许被新的 Request 继续引用。
