# Design

## Context

现有 WisDM 服务记录使用两张 DynamoDB 表：主表同时保存 `RECORD#<record_id>` 主记录、`SO#<normalized_so>` 唯一占位和全局计数器，历史表按 `record_id` 分区保存数量不设上限的 History。创建通过事务同时写入主记录、SO 占位和创建历史，更新使用 `version` 乐观锁；前端列表已有操作列和基于角色的权限上下文，但没有删除 API。

删除会跨两个表且 History 数量不固定，不能假设所有删除项都能放进一个 DynamoDB 事务。设计必须保证最终物理清理、可恢复重试以及 SO 占位不会误删或被并发写入重新占用。需求和可观察行为见 `proposal.md` 与 `specs/wisdm-service-management/spec.md`。

## Goals / Non-Goals

**Goals:**

- 让管理员删除任意误建记录，并让其他内部账号删除自己创建的误建记录。
- 最终清理主记录、SO 占位和所有 History，并释放 SO 供重新建档。
- 通过乐观锁和 SO 占位归属条件避免并发更新、自动补充与删除互相覆盖。
- 删除失败后保留列表记录，用户重新点击 Delete 即可重试，不引入额外恢复流程。

**Non-Goals:**

- 不提供批量删除、详情页删除、软删除、回收站或恢复功能。
- 不删除或修改来源预配置请求，不回收 WDM 编号。
- 不改变现有记录内容编辑、Workflow 或自动补充条件。

## Decisions

### 1. 删除入口仅放在列表并复用现有“管理员或创建者”权限

前端在每行现有 `Action` 列的现有按钮之后增加 Delete，不调整其他按钮顺序或列表布局：`admin` 对所有记录可见，其他 RAK 内部账号仅在记录的 `createdBy.id` 与当前用户 ID 一致时可见。点击后打开确认交互，正文同时展示 SO Number 与 WDM 记录号并说明不可恢复；确认期间禁用重复提交，成功后刷新 WisDM 列表缓存，失败则保留行并展示服务端错误。

后端新增 `DELETE /api/wisdm-service-records/{record_id}`，先执行内部账号认证，再按现有请求删除原则校验“管理员或记录创建者”。创建者比较使用认证用户 ID 与服务端保存的 `created_by.id`，不信任客户端字段。前端隐藏只是体验优化，服务端始终独立校验并在越权时返回 `403`。

自动建档记录继续使用现有 `created_by` 操作者快照：若实际触发保存的账号也是当前 RAK 内部账号，则该账号可删除；外部账号触发或创建者不匹配时，只能由管理员删除。备选方案是允许所有内部账号删除全部记录，但这会扩大不可恢复操作权限，因此采用与现有配置请求一致的“管理员删除任意记录、个人删除本人记录”。

### 2. History 清理后以条件事务删除主记录和 SO 占位

History 数量不受限，无法把所有 History、主记录和 SO 占位可靠地塞进单次事务。删除流程保持为两个直接步骤：

1. 分页查询该 `record_id` 的 History，使用批量写逐页物理删除并处理未处理项，直到再次查询为空。
2. 在同一事务中删除 `RECORD#<record_id>` 与 `SO#<normalized_so>`；主记录条件要求 `version` 仍与删除开始时一致，SO 占位条件要求其 `record_id` 仍指向目标记录。

只有第二步成功后接口返回成功。任何步骤失败均返回错误并保留列表行；有权用户重新点击 Delete 时重新读取最新版本、清理剩余 History 并再次执行最终事务。

备选方案是先删主记录再异步清 History，但失败时记录已从列表消失，用户无法直接重试且会留下孤立 History，因此采用先清 History、最后条件删除主记录和占位。

### 3. 使用记录版本协调并发写入

删除开始时保存目标记录的当前 `version`。内容更新、Workflow 更新和配置工单自动补充都会递增版本；如果它们在 History 清理期间成功，最终删除事务因版本不匹配而失败并返回 `409`。用户重新点击 Delete 后以最新版本重试，并再次清理并发写入产生的 History。

最终事务校验 SO 占位仍属于目标记录，避免异常数据或并发重建时误删其他记录的占位。删除成功释放占位后，现有手工创建和自动建档路径无需特殊分支即可为相同 SO 生成新的 WDM 编号。

### 4. History 批量清理保持分页和重试边界

数据层新增按页读取 History 键和批量删除能力，不把全部历史一次加载到内存。每页只传递 `record_id` 与 `event_key` 主键；批量写重试未处理项，并在进入最终事务前重新查询确认分区为空。

删除过程不新增删除 History，因为彻底删除要求该记录的全部 History 最终不存在。操作审计若将来有合规需求，应进入独立于服务记录生命周期的平台审计能力，不在本变更引入。

### 5. 错误语义与客户端恢复

- 目标主记录在删除开始前不存在：`404`。
- 非内部账号，或非管理员删除他人记录：`403`。
- 版本变化或 SO 占位归属变化：`409`。
- DynamoDB 清理失败：`500`，不返回成功，前端保留列表行并允许重试。
- 删除成功：返回明确成功响应；再次删除同一编号因主记录已不存在而返回 `404`。

前端不做乐观移除，避免后端部分失败时列表暂时丢失目标行。

## Risks / Trade-offs

- [跨表、无限 History 无法单事务删除] → 分页清理 History 后使用版本与占位归属条件事务完成最终删除；失败时保留列表记录供再次点击重试。
- [并发更新可能在 History 清理期间写入新历史] → 更新会递增版本，使最终删除返回 `409`；下一次点击会重新清理最新 History。
- [删除与配置工单保存并发可能导致一次 `409`] → 依靠版本条件避免覆盖；调用方重新加载后重试相应操作。
- [History 批量删除增加 IAM 权限] → 部署前为两张 WisDM 表补充 `DeleteItem`，并为历史批量写补充 `BatchWriteItem`，不修改凭证或 Region 配置。
- [自动记录的创建者可能不是可访问 WisDM 的内部账号] → 仅当认证内部用户 ID 与保存的创建者 ID 一致时开放个人删除，否则由管理员处理。
- [删除后来源请求再次保存会重建记录] → 这是已确认的物理删除语义；确认文案提示删除不修改来源工单，避免误以为永久阻止同步。

## Migration Plan

1. 为应用 IAM 角色补充 WisDM 主表和历史表的删除权限，并用运行身份验证单条删除与历史批量删除调用。
2. 部署数据层删除协调和后端 DELETE 接口，验证管理员删除任意记录、内部账号删除本人记录、越权拒绝、失败续删、并发冲突和同 SO 重建。
3. 部署前端列表 Delete、确认交互和缓存刷新。
4. 使用测试记录验证包含多页 History 的完整清理，以及来源工单再次保存后的自动重建。
5. 若需回滚，先移除前端删除入口，再回滚 DELETE 接口；已完成的物理删除不可恢复，删除失败且主记录仍存在的记录无需额外状态恢复。
