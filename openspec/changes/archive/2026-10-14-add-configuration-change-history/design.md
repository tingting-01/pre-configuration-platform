## Context

当前请求更新接口读取现有 Request 后构造 `update_data`，但 `configData` 只会覆盖 `config_data`，不会生成字段差异。创建、状态和分配活动通过 `preconfig-activities` 表保存；活动查询按 `request_id` 返回时间倒序数据。History 页面直接渲染该接口的数组，并依赖固定的基础字段。

Activities 表已经能够容纳不同活动类型的可选属性，因此本变更无需新增表或迁移旧数据。DynamoDB `TransactWriteItems` API 的 IAM 授权由事务内实际使用的 `UpdateItem`、`PutItem` 等操作以及可能存在的 `dynamodb:EnclosingOperation` 条件控制，不依赖独立的 `dynamodb:TransactWriteItems` IAM Action。需要同时处理三个约束：嵌套配置差异必须稳定且安全；配置与对应历史必须原子提交；新旧活动必须能在同一接口和现有 UI 中共同展示。

## Goals / Non-Goals

**Goals:**

- 在服务端准确计算 `configData` 的字段级变化，并复用现有 Activities 表保存一条配置变更活动。
- 保持 `/activities` 的原有响应结构和 History 卡片设计兼容。
- 让新活动不再依赖实时用户关联，并尽可能改善旧活动的 `Unknown User`。
- 控制历史数据体积：保留文件类配置的可读元数据摘要，同时避免记录敏感原值或原始大体积内容。
- 通过跨表事务保证配置变化和对应 Activities 历史同时成功或同时失败，并为事务失败提供足够且安全的诊断信息。

**Non-Goals:**

- 不保存完整配置快照，不提供版本号、版本比较、恢复或回滚能力。
- 不新增历史表，不迁移、重写或补录旧活动。
- 不改变 History 页面和活动卡片的主体结构，不增加新的历史入口；配置变更卡片内部可以增加分组、折叠和长值预览交互，但不改变状态、分配、评论或通知的业务规则。
- 不尝试从信息不足的旧活动中猜测操作者。

## Decisions

### 1. 复用 Activities 表，以可选字段扩展活动模型

新增活动使用 `activity_type = configuration_changed`，并在现有基础字段上增加：

- `changes`: 一次保存产生的字段差异数组；每项包含 `field`、`from`、`to`。
- `actor_name`: 活动发生时认证用户的姓名快照。
- `actor_email`: 活动发生时认证用户的邮箱快照。

`user_id`、`description`、`created_at` 和既有活动键保持不变。DynamoDB 允许旧活动缺少新字段，因此 API 和存储均可增量上线。

备选方案是把 `history` 数组内嵌到 Request，或新增版本表。前者会让 Request 持续膨胀并增加并发覆盖风险，后者超出“只查看字段变更历史”的需求；两者均不采用。

### 2. 后端基于已持久化旧值计算差异

只有更新请求显式包含 `configData` 时才计算差异。差异计算使用服务端从数据库读取的 `config_data` 作为旧值，不接受客户端提供旧值或历史内容。

递归比较规则：

- 字典递归到叶子字段，使用点分路径，例如 `network.wan.apn`。
- 字典键顺序不产生差异。
- DynamoDB `Decimal` 等数据库数值在比较前转换为普通 JSON 数值。
- 缺失字段、`null` 和空字符串按等价空值处理，以减少表单序列化造成的噪声。
- 数组作为一个字段比较，内容或顺序变化时保存整个数组的新旧安全值，不生成数组索引级差异。
- 一次请求的全部变化合并为一条活动；结果为空时不写活动。

备选方案是由前端计算或提交 `changes`。该方案无法防止篡改，也容易与数据库真实旧值不一致，因此不采用。

### 3. 用集中式策略分类处理普通字段、敏感字段和文件类字段

差异计算在写入活动前应用集中式字段处理策略：

- 普通配置字段按标准规则记录新旧值。
- 密码、密钥、令牌、私钥等敏感路径保留“该字段发生变化”的事实，但 `from` 和 `to` 使用固定脱敏标记。
- 扩展文件、配置文件和证书附件对象只提取名称、数量、大小等可读元数据形成摘要；内部文件 ID 不作为面向用户的主要变化内容。
- 原始二进制、Base64、完整证书正文或其他不可安全展示的大体积内容不写入活动；如果能够安全识别对应字段，则以不含原文的占位摘要记录该字段发生变化。
- 活动描述只说明配置被更新，不拼接配置原值。

字段分类、摘要转换和脱敏规则应集中维护并以单元测试锁定，避免散落在接口分支中。当前配置中的 `extensionFiles`、`configFiles` 以及证书对象主要保存文件元数据，因此不得因“文件字段”而整体丢弃。备选方案是仅在前端隐藏敏感值或大体积内容，但原始内容仍会落库，不满足安全约束，因此不采用。

### 4. 使用 DynamoDB 事务原子保存配置与活动

当 `changes` 非空时，数据访问层使用一次 `TransactWriteItems`，其中包含对 `preconfig-requests` 的 `Update` 和对 `preconfig-activities` 的 `Put`。事务成功时两个写入同时生效；任一写入失败时整体取消，接口返回更新失败。没有配置变化时继续使用现有 Request 更新路径；状态和分配活动逻辑保持现状。

事务请求使用 DynamoDB 低层客户端要求的 AttributeValue 格式序列化 Request Key、更新值和 Activity Item。IAM 应授权事务实际涉及的表和操作；若普通写入可用但事务仍被拒绝，需要继续检查资源策略和 `dynamodb:EnclosingOperation` 条件，而不是假设存在独立的事务 IAM Action。

捕获 `ClientError` 时记录 Request ID、事务操作对应的表、AWS 错误码、错误消息、经筛选的 `CancellationReasons` 以及 AWS RequestId。取消原因仅保留索引、操作名、Code 和 Message，不记录其中可能包含敏感配置的 Item，也不记录 Request 更新值或 Activity 内容。

备选方案包括 Request Outbox、简单顺序写入和永久内嵌历史。Outbox 需要处理暂存、转存、清理、去重、并发控制、失败恢复和活动合并，只有确认事务因不可调整的策略限制而不可用时才考虑；简单顺序写入存在永久丢失历史的窗口；永久内嵌会持续放大 Request，均不作为当前实现。

### 5. 活动查询采用快照优先、批量关联、受控解析的身份解析顺序

读取活动时按以下优先级生成现有响应字段 `authorName` 和 `authorEmail`：

1. 活动自身的 `actor_name`、`actor_email`。
2. 收集本次全部活动的 `user_id`，一次批量关联用户表。
3. 对没有快照且无法关联的旧活动，按活动类型使用受控的已知描述格式解析操作者。
4. 仍无法确定时返回未知占位符。

描述解析只识别已知格式中的操作者位置，不做任意邮箱搜索，避免把被分配人识别为操作者。新活动的身份字段全部来自认证上下文，客户端不能覆盖。

前端显示操作者时将 `Unknown User` 和 `unknown@example.com` 视为占位符；有效姓名优先，否则显示有效邮箱，最后才显示 `Unknown User`。

### 6. API 只做加法扩展，前端在现有卡片内分组并按需展开

`GET /api/requests/{request_id}/activities` 继续返回活动数组，并保留 `id`、`activityType`、`description`、`createdAt`、`authorName`、`authorEmail`。仅为适用活动增加可选 `changes`。

History 组件继续使用现有卡片结构：

- `changes` 缺失或为空时走原有渲染路径。
- `changes` 非空时，在描述和作者时间信息之间追加变更区域，并按 `changes.field` 的第一个路径段分组。
- 已知顶层模块使用固定的用户可读名称：`general`、`network`、`lora`、`system`、`extensions` 和 `other` 分别映射到对应配置区域；未知模块根据原始路径段生成可读兜底名称，不能因此丢弃变化。
- 分组顺序保持其字段首次出现在 `changes` 中的顺序；分组标题显示模块名称和变化数量。每组默认折叠，展开后展示全部字段变化，并允许再次收起。
- 组内字段标签移除已由分组标题表达的顶层路径段；完整字段路径仍作为辅助信息保留，避免标签简化后失去定位能力。
- 对象和数组使用安全 JSON 格式化，空值使用统一占位符。
- 格式化后的单个旧值或新值超过 100 个字符时，默认显示前 100 个字符和省略标记，并提供 `Show more` / `Show less` 独立展开或收起；该阈值属于前端展示实现参数，不改变 API 数据和后端历史存储内容。
- 未识别活动类型继续使用现有默认图标和样式。

不增加新的页面、筛选、版本入口或恢复操作。

## Risks / Trade-offs

- [空值等价规则可能隐藏 `null` 与空字符串的语义区别] → 仅用于历史差异降噪，并通过覆盖真实表单数据的测试确认这些值在当前配置模型中等价。
- [数组整体记录可能产生较长活动] → 不做索引级差异以控制实现复杂度；文件类数组先转换为名称、数量和大小摘要，其他复杂值设置合理的序列化与展示长度限制。
- [分组默认折叠可能降低变化明细的可发现性] → 分组标题始终展示模块名称和变化数量，并使用可访问的展开状态和明确的箭头交互提示用户查看明细。
- [长值预览可能被误解为后端已截断] → `Show more` 展示接口返回的完整格式化值；前端预览只控制显示，不替代后端对敏感内容和大体积原始内容的过滤。
- [文件元数据摘要可能丢失内部实现细节] → History 面向用户展示可理解的文件变化，内部文件 ID 仍保留在 Request 当前配置中，但不作为审计展示内容。
- [敏感字段命名新增后未进入规则] → 使用显式路径列表结合敏感名称模式，并为典型与新增字段维护测试。
- [旧描述格式变化导致解析失败] → 解析失败时保持 `Unknown User`，不影响活动本身展示，也不猜测身份。
- [事务可能因权限、验证、冲突、容量或 Item 大小等原因失败] → 记录安全的结构化诊断字段，并依据真实 `Error.Code` 和 `CancellationReasons` 处理，不根据单一 500 响应猜测原因。
- [事务冲突会使本次保存失败] → 保持原子失败语义，不退化为部分写入；如生产日志确认存在可重试冲突，再单独评估有限重试。
- [混合版本部署期间前后端能力不同] → 新字段全部可选；先部署后端时旧前端会忽略新增字段，先部署前端时旧响应仍走原渲染路径。
- [现有项目缺少相关自动化测试] → 将纯差异函数、身份解析和 API 混合数据兼容测试列为实现必需任务。

## Migration Plan

1. 增加差异计算、过滤规则、操作者快照和 Request/Activity 跨表事务写入能力，并保持现有 API 字段不变。
2. 部署后端；旧前端会忽略新增的 `changes`，既有活动无需迁移。
3. 更新 History 组件以条件展示 `changes` 和正确回退操作者。
4. 验证事务成功、Request 更新失败、Activity 写入失败、无变化保存、敏感字段及旧 `Unknown User` 兜底。
5. 如需回滚，停止生成新的配置变更 Activity，并回滚事务写入和前端条件渲染；已经生成的活动无需删除。
